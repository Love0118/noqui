# Noqui bridge v1

The Minecraft plugin owns the one shared quiz room, authenticated player identity, private answer catalogue, scoring and authoritative timeline. Rust prepares each unique YouTube ID once, serves cached Ogg Opus bytes, and publishes a safe browser projection. The browser never controls scoring or advances a round.

Website: `https://noqui.danta.qzz.io`. Minecraft remains `mud.danta.qzz.io`. Public HTTP binds only `127.0.0.1:8787`; trusted plugin HTTP binds only `127.0.0.1:8788`. The TLS proxy must never expose `/internal/` or the internal port. There is no CDN/provider layer.

Public Minecraft resource-pack/skin files under `/packs/` are served directly by Nginx from `/var/www/noqui/packs/`, outside the Rust audio/authentication routes. GET/HEAD downloads require no browser session cookie. Install only reviewed public files with content-hashed filenames: successful static responses use `public, max-age=31536000, immutable`. Directory listing and symbolic-link access are disabled; the alias directory and its parent components must be real directories. Keep private quiz metadata and unhashed changing files outside this public directory.

## Internal authentication

All four internal routes require `Host: 127.0.0.1:8788`, `X-Noqui-Key-Id`, `X-Noqui-Timestamp` (Unix seconds), `X-Noqui-Nonce` (base64url, at least 16 random bytes) and `X-Noqui-Signature: v1=<lowercase hex HMAC-SHA256>`. The shared secret is exactly 32 raw bytes. Sign this UTF-8 text without a trailing newline:

```text
UPPERCASE_METHOD
EXACT_REQUEST_PATH
TIMESTAMP
NONCE
lowercaseHex(SHA256(exact request body bytes))
```

Queries are rejected. Empty GET body hashes the empty byte string. Clock skew is at most 30 seconds; nonces cannot repeat for 120 seconds. Retry with a new nonce/signature and unchanged idempotent body. Bodies are bounded to 64 KiB. JSON request objects reject unknown fields. IDs are canonical lower-case UUIDs; sequence/revision values are unsigned decimal strings without leading zeroes. Times and positions are integer milliseconds.

## Plugin routes

| Route | Request | Response |
|---|---|---|
| `POST /internal/v1/media/jobs` | `{schemaVersion:1,requestId,videoId,song?:{title,tags}}` | `202` pending, `200` cached READY; `{jobId,state,mediaId,profileVersion,durationMs,byteLength,mime,failureCode,retryable,retryAfterMs}` |
| `POST /internal/v1/catalogue/import` | `{schemaVersion:1,songs:[{id,youtubeUrl,title,tags}]}`; at most 50 records and the existing 64 KiB body limit | `200 {savedCount:<batch length>}`, including idempotent records; whole-batch transaction |
| `GET /internal/v1/media/jobs/{jobId}` | Empty body | Same job descriptor |
| `POST /internal/v1/sync` | Full snapshot below | `{acceptedSeq,backendEpoch,serverTimeMs,authorityLeaseMs:15000,browsers:[...]}` |
| `POST /internal/v1/join-tokens` | `{schemaVersion:1,requestId,instanceId,uuid,membershipId,roomId,tokenSha256}` | `201 {expiresAtMs,expiresInSeconds}` |

`videoId` is exactly 11 ASCII YouTube ID characters. The plugin parses the native dialog's HTTPS YouTube URL locally; title/tags/aliases remain private. Ingest accepts the video ID rather than an arbitrary source URL; catalogue import accepts only validated canonical YouTube URLs as metadata and does not start downloads. Missing tools/source authentication and source/network failures become explicit FAILED jobs. A successful registration is not playable until READY. Poll pending jobs at least two seconds apart; failed retryable jobs need a new explicit request after the 30-second cooldown, except evicted/missing-cache jobs which can requeue immediately. Same request ID with changed video/token/metadata returns `409 IDEMPOTENCY_CONFLICT`. Concurrent requests for the same video/profile share one job.

The single background worker drains every accepted job independently of current round selection; one failed conversion does not stop later jobs. Up to 64 queued sources are accepted. Further registrations return `429 QUEUE_FULL` with a two-second retry hint and do not create a request receipt, so callers can retry the same request ID. Time spent queued is separate from the 300-second per-attempt processing deadline; consumers must allow for preceding jobs rather than treating a valid queued job as a conversion failure. Future queued/READY media remains private and cannot be selected through a public browser endpoint before it is that room's current asset.

Snapshot shape (listed fields are required except the optional room progress pair described below; nullable fields accept JSON null):

```json
{
  "schemaVersion": 1,
  "instanceId": "<plugin lifetime UUID>",
  "seq": "1",
  "sentAtMs": 1792600000000,
  "roster": [{
    "uuid": "<authenticated Minecraft UUID>",
    "membershipId": "<current join/room generation UUID>",
    "nickname": "PlayerOne", "textureHash": null, "roomId": "<room UUID>"
  }],
  "rooms": [{
    "roomId": "<room UUID>", "roomRevision": "1", "phase": "PREPARING",
    "roundNumber": 1, "totalRounds": 100, "registeredSongs": 3,
    "round": {
      "roundId": "<round UUID>", "number": 1, "revision": "1",
      "playbackGeneration": "<audio load generation UUID>", "mediaId": "<READY media UUID>",
      "clipStartMs": 0, "clipEndMs": 40000,
      "anchorPositionMs": 0, "anchorAtMs": 1792600003000, "playing": false,
      "playbackRate": 1
    },
    "reveal": null
  }]
}
```

Send every two seconds and immediately on membership/phase/timeline changes, using one asynchronous in-flight request and coalescing obsolete heartbeats. Keep arrays for wire compatibility; v1 accepts at most one room and 64 players. Omission revokes membership and its tokens/sessions. `membershipId` changes on a new actual join or room membership generation. Read UUID/name/skin hash from the authenticated PlayerProfile, never from browser claims/IP or a third-party identity lookup.

Room progress `roundNumber` and `totalRounds` are optional for older plugin compatibility. Supply both integer values together, or omit both (both null also means absent). `totalRounds=0` means unlimited; positive limits accept `1..2147483647` (Java `Integer.MAX_VALUE`). `roundNumber` is a nonnegative unsigned 32-bit integer (`0..4294967295`); for a positive limit require `roundNumber <= totalRounds`, while zero imposes no total-based bound. The plugin applies its own Java counter cap. A non-null `round.number` must remain positive and equal `room.roundNumber` when the pair is supplied. The round object itself is unchanged.

New plugins send the pair in every phase, including IDLE/ENDED when the round object is null. Plugin commands `/noqui start` select unlimited play, `/noqui start 200` select a positive limit, and `/noqui limit N` change that independent round cap. `totalRounds` is not the browser's display denominator. A live limit change updates room progress with a new room revision; it does not require changing the audio round object or timeline. The plugin owns command handling, counter caps, limit changes and round transitions.

Optional room field `registeredSongs` is a nonnegative unsigned 32-bit integer (`0..4294967295`); omitted or null means unknown and is omitted from the public projection. Negative, fractional, boolean, string and overflowing values are rejected. It counts registered submissions in this quiz session, including already started/played songs plus valid unplayed current/queued submissions. Unplayed cancellation/failure removes a submission; completing a played song retains it; a new session resets the count. It is not the saved catalogue size, remaining queue length, round limit, or number of deduplicated cache pins, and is independent of `totalRounds`.

When both `roundNumber` and `registeredSongs` are available, the browser label is exactly `current/registered`, for example `1/3` or empty-session `0/0`, without padding, spaces around the slash, middle-dot separators or an unlimited marker. Older snapshots without the registered count show only the known round or the waiting-room label and never invent a denominator from the limit. Count-only room revisions preserve the round ID, playback generation, rate and audio timeline. Deploy the Rust decoder before Java sends `registeredSongs`; older strict decoders reject the additive field.

`seq` increases per full snapshot; duplicate identical seq/body is idempotent but does not renew the 15-second authority lease. Lower seq or changed content at the same seq fails. Room/round revisions cannot move backward or change their corresponding content at the same revision. Preserve `instanceId` across hot reload; a different instance waits for the old authority lease to expire. A backend restart returns a new `backendEpoch` and accepts the current full snapshot.

The internal sync snapshot accepts optional top-level `retainedMediaIds`, a full deduplicated array of at most 100 canonical media UUIDs. Every listed ID must reference a valid READY file in the current profile. Invalid IDs, duplicates, null/non-array values and oversized lists are rejected; an unavailable referenced asset returns retryable `409 MEDIA_NOT_READY`. This field is private queue metadata and never appears in public state/SSE. An accepted pin-aware snapshot replaces the durable queue pin set; `[]` explicitly releases it. An omitted legacy field preserves existing queue pins and disables eviction. Rust also protects the current round independently. A restarted Rust process retains persisted pins but does not evict until a valid pin-aware sync arrives. Authority expiry and transport gaps do not release pins. Stale/rejected instance/sequence updates and late completion of an older cancelled HTTP request cannot replace newer pins.

Java retains each prepared submission's media until its existing cancellation/completion path releases that reference, including duplicate references to the same media. It must receive a successful sync acknowledgement containing the pin before delivering READY to the game. New READY commits and cache hits have a 60-second temporary handoff guard; this is not a lease for indefinitely queued submissions. Cancellation/failure before acknowledgement must not expose unprotected media. Deploy the Rust decoder before Java starts sending `retainedMediaIds`; older decoders reject the extra field. Legacy clients can still ingest when there is room, but cannot enable safe automatic eviction.

`round.playbackRate` is an optional integer number `1` or `2`, defaulting to `1` when omitted; all other values are rejected. Public round snapshots include the effective rate. `clipStartMs`, `clipEndMs`, `anchorPositionMs`, browser `positionMs` and `bufferedUntilMs` always use cached source-media milliseconds, while `anchorAtMs` is wall-clock milliseconds. For a playing round the expected source position is `min(clipEndMs, max(clipStartMs, anchorPositionMs + max(0, serverNow - anchorAtMs) * playbackRate))`; a paused round stays at its anchor position. A resumed countdown supplies a new wall-clock anchor and keeps the same source position/rate. Remaining wall time in milliseconds is `ceil((clipEndMs - expectedSourcePosition) / playbackRate)`; during pause/countdown the expected source position equals the anchor. The same cached 120-second asset therefore lasts 60 wall seconds at rate 2. No new encoding or cache profile is introduced.

The rate is frozen for each `roundId`; changing it on that ID is a revision conflict even when the revision increases. Plugin mode changes apply to the next round. The browser sets both default/current playback rate and sets `preservesPitch=false` at rate 2 to match the original doubled-pitch mode; normal rate 1 restores pitch preservation. Progress and elapsed/remaining labels use wall time, seeking and readiness telemetry use source time, and PREPARED requires half a wall second of source buffering (one source second at rate 2), capped to clip end. Deploy this Rust/browser version before a plugin sends `playbackRate`: older strict snapshot decoders reject the new field.

Phases: IDLE, WAITING_FOR_MEDIA, PREPARING, COUNTDOWN, PLAYING, PAUSED, REVEAL, ENDED. IDLE/ENDED can have null round; WAITING_FOR_MEDIA can have null round or null mediaId. PREPARING/COUNTDOWN/PLAYING/PAUSED require a READY asset and coherent bounds. Clips start at offset zero, default to 40 seconds, and last at most **120 seconds**, capped to actual audio length; positions are relative to the cached first-120-second file. No arbitrary source-offset feature is provided. COUNTDOWN schedules a future anchor, normally **three seconds** ahead. The browser stays paused until the anchor. PLAYING requires playing=true; idle/pending/preparing/paused/ended require false. REVEAL permits either true or false: a first correct answer can reveal while the original timer/audio continues. Stop/skip/cancel/recovery snapshots may move directly to IDLE/REVEAL/ENDED; there is no restrictive phase ladder. REVEAL→IDLE with null round clears the player for the next submitter.

COUNTDOWN can remain after its scheduled anchor while browser playback is delayed. Its expected source position and displayed round progress stay at `anchorPositionMs`; the browser attempts playback from that saved position, without seeking forward by elapsed wall time. Once playback starts, it continues naturally without being rewound on COUNTDOWN heartbeats. The plugin confirms the first start only after a current-member/current-round/current-generation PLAYING report whose `lastSeenAtMs` is at or after the scheduled anchor, no more than five seconds old, and whose `positionMs` is greater than the saved anchor and no greater than clip end. It bounds the reported advance to two wall seconds times playback rate, adds at most two seconds of report-age compensation, and caps the result at clip end. It then publishes PLAYING with the same generation and an adjusted authoritative anchor. Round counting, ticket spending, answers and the round end timer begin only on that confirmation; resume generations require new proof. The browser adopts the confirmed anchor. Deploy this frontend together with the plugin's start-confirmation behavior: the old frontend can falsely report PLAYING and the old plugin advances the round without confirmation. No wire field or status is added.

Before REVEAL, `reveal` must be null and no title, tags, aliases, videoId or source URL may appear in the snapshot. At reveal it can be `{title,aliases:[],tags:[],youtubeUrl:"https://www.youtube.com/watch?v=<id>"}`. The Rust job registry's private source ID is never part of a public DTO. Current file URLs, document/MediaSession titles and file metadata do not contain the answer. Future audio is not preloaded.

Browser entries in the sync response contain `uuid,membershipId,online,leaseExpiresAtMs,clientId,roundId,roundRevision,playbackGeneration,status,positionMs,lastSeenAtMs`; absent session fields are null. Browser telemetry supplies readiness/start confirmation; it does not authorize answers or award score. PREPARED must match the intended round revision/generation and indicates buffering, not proof that browser policy permits output. Native logic should use a visible preparation timeout/skip decision rather than treating a disconnected browser as ready.

Each entry also contains the additive boolean `connected`, for connection prompts independently of media readiness. It is true only for an unexpired session matching that UUID, membership and room, with valid Minecraft authority and a successful authenticated state/SSE read or accepted playback report in the last 20 seconds. SSE's five-second heartbeat renews this connection signal even when no media is selected or playable. Token redemption, `/me`, clock/media requests, rejected CSRF writes and expired/revoked sessions do not establish presence. Activity expires after 20 seconds without another control read/report; it does not require PREPARED. Existing `online` retains its 60-second active playback-client-lease meaning. Consumers should use `connected` when present and may fall back to `online` with older backends; connection prompts must still be gated by the plugin's quiz-active state.

## Browser authentication and control

The plugin generates 32 random bytes, base64url encodes them without padding (43 characters), registers **SHA256 of the token's UTF-8 string**, and privately sends `https://noqui.danta.qzz.io/join#t=<token>`. New issuance revokes the older outstanding token; expiry is 60 seconds. Redemption consumes the token atomically and creates a new opaque session. A lost successful response requires a new in-game link.

The join page automatically redeems once, removes the token fragment, notifies older tabs of the identity change and starts the player in the same document and audio element. It changes the address to `/` with history replacement, without navigating away and losing document visibility/interaction history. `/` and `/join` serve the same player HTML; `/join.js` starts `/app.js` only after successful redemption, or directly for an ordinary home visit. Invalid/expired tokens or failed redemption do not start the player or adopt an older cookie identity. There is no additional browser consent screen. Clicking Minecraft's external-link action is not a gesture in the web document: a newly opened browser may still require its first visible visit and real page click/key before unmuted audio. The ordinary player control is the fallback; no browser/global autoplay setting is changed.

| Route | Behavior |
|---|---|
| `POST /api/v1/auth/redeem` | `{token}`; exact Origin + JSON; returns `{me,csrfToken,sessionExpiresAtMs}` and a Secure/HttpOnly/SameSite=Strict/Path=/ `__Host-noqui` cookie |
| `GET /api/v1/me` | Same safe identity/CSRF/absolute expiry descriptor |
| `GET /api/v1/time` | `{receivedAtMs,sentAtMs}` for minimum-RTT clock estimation |
| `GET /api/v1/state` | Current room-only safe snapshot |
| `GET /api/v1/events` | SSE: immediate `state`, later state updates and five-second `lease`; transient `offline` on unavailable authority; `revoked` then close on actual session expiry/revocation |
| `POST /api/v1/playback` | `{clientId,takeOver,roundId,roundRevision,playbackGeneration,status,positionMs,bufferedUntilMs,lastEventId}`; returns `{serverTimeMs,leaseExpiresAtMs,activeClientId,heartbeatAfterMs:15000}` |
| `POST /api/v1/auth/logout` | `{}`; revoke the authenticated session/SSE server-side; no Set-Cookie deletion that could erase a newer concurrent login |

All authenticated writes require the exact Origin `https://noqui.danta.qzz.io`, JSON and `X-Noqui-CSRF`. One session per UUID/current membership; new redemption replaces old login. The HttpOnly cookie represents one player per browser profile: a successful redemption also retires the prior session identified by that request's cookie, including a different player UUID. Invalid redemptions preserve the current login. Concurrent players should use separate browser profiles; no per-tab bearer credential is introduced. Older tabs stop on the non-secret login-change notification, a mismatched player identity, or `403 CSRF_REJECTED`, and never silently adopt the newer cookie/CSRF or log it out. Logout revokes only its authenticated server-side session; it leaves the now-invalid cookie untouched so a delayed response cannot clear a later login cookie.

Idle timeout is 30 minutes, absolute expiry eight hours, matching cookie Max-Age=28800 and `sessionExpiresAtMs`. The 60-second one-time join-token expiry never expires its already-redeemed session. Active authenticated reads, SSE heartbeats and playback reports renew idle time only while authority is valid; they never extend the absolute cap. A 15-second authority gap suspends room state, playback writes, media and token redemption with `503 PLUGIN_OFFLINE`; it does not delete an otherwise unexpired cookie. Existing SSE sends `offline` without room data and stays open. The client pauses at authority expiry and recovers automatically when a fresh higher-sequence snapshot restores the same instance/UUID/membership/room. A duplicate sequence does not restore authority. Membership removal/change, a new plugin instance, logout, idle expiry or absolute expiry revoke the old session permanently, even if the old roster later returns. Own-session `/me` and logout remain available during a short authority gap; offline requests do not renew idle time. IP addresses never choose identity.

Each loaded document has a fresh `clientId`, including duplicated tabs whose sessionStorage was copied. A second tab requires explicit takeover or expiry of the 60-second browser lease. Browser telemetry renews at most every 15 seconds when unchanged; new round revision/generation or playback-status changes report immediately, including media-ready PREPARED while hidden. SSE state/lease callbacks also drive renewal when background interval timers are throttled. Reports are coalesced and transient failures back off at least two seconds. An apparently OPEN stream with ten seconds of silence triggers a single-flight state refresh; playback still stops at the backend's exact 15-second authority deadline and the client lease deadline. Temporary SSE transport loss reconnects with the same session and leaves an otherwise valid timeline playing until its real lease deadline. Returning to a visible tab refreshes state immediately. A fully suspended/offline browser cannot keep an expired authority alive. Statuses: CONNECTED, NEEDS_GESTURE, LOADING, PREPARED, PLAYING, PAUSED, BUFFERING, FAILED. Stale-round readiness cannot prepare the current round. Internal preparation states display concise idle text; preparation progress and ready messages are not shown, while playback errors remain visible.

During COUNTDOWN, naturally progressing PLAYING reports renew every second until the plugin confirms the start, so their existing timestamp remains fresh. PLAYING requires a fulfilled play promise and at least 100ms of continuous source progress times playback rate over at least 100ms wall time. Pending play promises, seeks, discontinuous position jumps and buffering cannot establish proof; more than two seconds without observed progress clears it. Media/generation changes reset proof, while revision-only updates preserve it and report against the new revision. Seek correction waits two seconds after a seek finishes and does not interrupt a pending play request. This confirms browser media-clock progress, not physical speaker audibility.

Public state contains `eventId,serverTimeMs,authorityLeaseExpiresAtMs,me,room,round,media,reveal`; `room` has `roomId,revision,phase,players` and, when supplied by the plugin, `roundNumber,totalRounds,registeredSongs` with the constraints above. Unknown optional counts are omitted from public room DTOs for older snapshots. Player entries have `uuid,nickname,textureHash,browserOnline`. `round` uses the snapshot round fields. `media` is `{mediaId,url:"/media/<sha256>.ogg",mime:"audio/ogg; codecs=opus",durationMs}` or null. `reveal` is null until accepted REVEAL. A new SSE connection always gets the current snapshot, so old/future events are not replayed. Disable proxy buffering and use timeouts longer than the heartbeat interval.

## Cached media and jobs

Song title, tags and canonical YouTube URL are stored privately in `song_catalogue` in Noqui's existing `media.sqlite`, independently of jobs, cache files and eviction. Each submission UUID is one immutable record. New job requests may include `song:{title,tags}`; the server derives `https://www.youtube.com/watch?v=<videoId>` and uses `requestId` as the catalogue ID. Metadata is saved atomically with an accepted registration before conversion, including queued songs and cache hits. Queue rejection or a registration storage failure rolls back the catalogue write. Exact retries retain the existing record and timestamps; a changed payload under the same ID returns `409 IDEMPOTENCY_CONFLICT`. Legacy requests without metadata remain supported.

The private HMAC-protected catalogue import route supports bounded migration from the plugin's existing song records. It validates schema 1 and canonical URLs, accepts an empty batch, and commits every row together. Its `savedCount` acknowledges the input batch length, not just newly inserted rows, so retrying an acknowledged batch returns the same count. Conflicts or invalid rows fail the batch without partial writes. Java keeps its original file until the relevant import acknowledgements are received and owns its backup/retirement. Catalogue records survive cache eviction, failed conversion, request-receipt pruning and service restart. They do not determine this quiz session's `registeredSongs` count. Neither public state/SSE, media/job responses nor a public catalogue endpoint exposes titles, tags or source URLs before the ordinary authorized reveal. Moma's databases and cache remain separate.

`GET/HEAD /media/{sha256}.ogg` requires a current session and that room's current asset. Hashes are exact lower-case SHA256 values registered READY, not authorization tokens. Single byte ranges, open/suffix ranges, HEAD, conditional ETag/Last-Modified, If-Range and 416 are supported. Unsupported multiple/malformed ranges fall back to full 200. Responses use `audio/ogg; codecs=opus`, Accept-Ranges, strong ETag, and `private, max-age=31536000, immutable`. Audio is never gzip/Brotli transformed. Streams use 64 KiB buffers, at most four concurrent streams/session and 64 total. Browser cache/downloaded bytes cannot be revoked; this is not DRM.

Profile `opus-48-clip120-source360-v3`: ffmpeg libopus, nominal 48kbps stereo 48kHz constrained VBR, one conversion per video/profile, no video/artwork/answer tags. Encode/cache only the first 120 seconds (or the shorter source) with FFmpeg `-t 120`; output validation permits up to 120.05 seconds for container/codec padding. Full client read-ahead is therefore bounded to about **0.72 decimal MB** at the nominal rate instead of about 1.8MB for a 300-second file, before container/TLS/HTTP overhead and VBR variation. The rate remains about 0.36MB/minute/listener. Current Chrome/Firefox/Edge and Safari 18.4 on supported OS versions are candidates; the client checks Ogg Opus support and reports failures visibly. Authenticated playback attempts automatically after the active-client lease is accepted, media is ready, and the authoritative timeline permits audio. There is no separate enable/consent button. If browser policy rejects `play()` with `NotAllowedError`, the status stays `NEEDS_GESTURE` and a trusted pointer/click/key interaction retries; browser/OS restrictions are not bypassed. Local pause persists across ordinary page interactions and new rounds until the ordinary playback control resumes. Muting/volume changes do not imply pause or alter the server timeline, and stale media/generation completions cannot mark a newer source blocked.

Dedupe and READY media selection are profile-specific. The prior `opus-48-clip40-source360-v2` profile remains eligible for already accepted rounds during a live upgrade; new submissions use the 120-second profile. Older full-length and 115-second profile files are not eligible for the 120-second profile's playback; a new registration creates/reuses the clipped job. Job status reports its actual stored profileVersion, including for older job IDs. Older queued profiles are not processed by the current worker. Older cached profiles participate in the same Noqui LRU budget.

When audio is paused and no play attempt is pending, the ordinary control shows `재생`; clicking it while media is loading keeps the user's play intent until readiness and the authoritative timeline permit playback. Genuine pointer/key events (including the existing reconnect control) can retry browser-blocked audio. If an older `play()` rejection arrives after such an event, the client makes one fresh attempt; another denial remains `NEEDS_GESTURE` and does not produce an autoplay retry loop. Explicit user pause, stored mute/volume, session revocation and active-client/timeline guards remain authoritative. See the [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay) and [WebKit media-element guidance](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/); a connection token alone does not grant unmuted autoplay permission.

Each new ingest resolves the YouTube metadata once with the same audio-format selector used for download. After checking the source ID/type, live flag and original duration, it writes a private resolved-info file and downloads with yt-dlp `--load-info-json`. The webpage/original URL fallback is removed from this file so a failed download does not silently repeat YouTube extraction; a later explicit retry resolves fresh URLs. Sources longer than 120 seconds use `--download-sections *0-120` with the configured FFmpeg; shorter sources keep the native full-audio download path. Container headers/indexes and read-ahead can require additional bounded range requests, so this is not an exact network-byte cap. The final FFmpeg encoder settings, 48kbps stereo Opus profile, single worker, process-group deadlines, source/workspace limits and immutable READY cache remain the same.

Spawned ingest tools emit one redacted `media_stage` diagnostic per completed stage, with `jobId`, `stage`, `elapsedMs` and `result`. Stages are `metadata`, `download`, `sourceprobe`, `encode` and `verify`; diagnostics contain no source URL, title, cookies or raw subprocess output. A `media_source` entry records the video ID, resolved duration and active limits, and `media_rejected` records the job/video IDs and final failure code without cookies or raw tool output. These timings distinguish upstream/authentication failures from transfer or encoding latency. Authentication rejection is not corrected by the performance path, and an anonymous fallback is not enabled without successful verification.

On Linux, yt-dlp and its FFmpeg range downloader remain in the job's owned process group. Both the subprocess deadline and cancellation of the enclosing async job kill that group, including child processes. The 25MiB Unix per-file limit is inherited by those children; the original 360-second source-duration check, 300-second attempt deadline, 150-second download-stage deadline and workspace checks still apply independently of the 120-second clip request.

Limits: one job, queue 100 (matching the room's 100 accepted submission slots), private source 360s/25MiB, cached output 120.05s/25MiB, temporary workspace 64MiB, logs 1MiB/file, total attempt deadline 300s. Prefer `bestaudio[ext=webm][abr<=80]`, falling back to the existing WebM/M4A selection when no matching low-bitrate WebM source is available. The worker checks actual files while processes run, kills its process group/tree on timeout/cancellation, and uses a Unix file-size limit. yt-dlp gets only an internally constructed canonical YouTube URL, a YouTube-only extractor, finite network retries and optional local cookie path. ffmpeg/ffprobe accept local files and a file/pipe protocol whitelist; source containers are restricted. There is no arbitrary URL/proxy endpoint. External downloader traffic is a separate process: host-level private/link-local/metadata egress denial remains a deployment responsibility, since Rust cannot enforce every DNS/redirect chosen inside yt-dlp.

Noqui's cached clip budget is **5 GiB (5,368,709,120 bytes)**, separate from its bounded temporary workspace and SQLite metadata. It applies only to Noqui's configured `media/` directory and `media.sqlite` registry, normally `/var/lib/noqui/media` and `/var/lib/noqui/media.sqlite`. Moma BGM caches, `bgm-work`, `bgm.db`, cloudpacks, resource packs, sibling directories and backups are neither counted in this budget nor traversed, touched or deleted. Existing shared YouTube-cookie authentication is unchanged.

Before each new ingest, the worker reserves up to 25 MiB of final-cache capacity and checks actual filesystem space, requiring 128 MiB free for the existing 64 MiB temporary bound plus 64 MiB headroom. It evicts unprotected Noqui files in persistent least-recently-used order until both limits are satisfied; the 5 GiB limit does not imply that 5 GiB is physically available. If active/queued/streamed/handoff-protected files or insufficient reclaimable space prevent admission, the job fails retryable `DISK_FULL` without deleting unrelated data. Current media, acknowledged queue pins and every open HTTP media response remain protected; stream protection lasts through response completion or body cancellation.

A new accepted enqueue request, reuse of a READY source, selection of a new logical round, and an authorized media GET update use order. Replaying the same idempotency receipt, job-status polling, HEAD requests, state reads and pin/control heartbeats do not. The order persists across restarts; legacy rows are initialized once from their existing job timestamps because historical usage was not recorded. Reusing an older song makes it recent. Eviction transactionally changes all referring jobs to retryable `CACHE_EVICTED`, clears their media IDs and journals the pending unlink before removing the file. A new request for an evicted or missing source re-enqueues the existing job immediately. Restart completes journaled deletions, invalidates missing READY files, and removes uncommitted generated SHA256 `.ogg` orphans only inside Noqui's media directory; unknown filenames and symlinks are not followed into other caches. Publishing holds the same cache/database lock across the final rename and READY commit. Partial temporary directories are discarded at startup. There is no public delete/repair endpoint.

Errors are `{error:{code,message,retryable,retryAfterMs,requestId}}`, with 400 validation, 401 authentication, 403 Origin/CSRF/membership, 404 private missing resource, 409 revision/idempotency/active-client/not-ready, 413 body limit, 422 source/timeline/answer-boundary, 429 queue/rate and 503 authority/tool availability. HTTP body-limit extractor rejection can be plain 413. Retry safe reads/idempotent writes on transport/429/5xx with bounded backoff; never replay a token redemption. No raw secrets, tokens, cookies, private answers or downloader stderr are sent in errors or application logs.

## Runtime and checks

Build/test from `noqui/web`: `cargo build --release --locked`, `cargo test --locked`, `cargo clippy --all-targets -- -D warnings`, `node --check static/app.js`, `node --check static/join.js`, `node --test tests/browser.cjs`.

The `noqui-web` CI job runs the Rust tests and dependency-free browser regression suite, with Node 22 selected explicitly.

Runtime environment:

| Variable | Value/default |

| `NOQUI_BRIDGE_SECRET_FILE` | Required file containing exactly 32 raw secret bytes, shared with the plugin |
